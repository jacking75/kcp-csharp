# 부록 B. FAQ

## 기본

### Q1. TCP 대신 항상 KCP를 써야 하나요?

**아닙니다.** KCP가 유리한 경우는 분명합니다.

| KCP가 유리 | TCP가 유리 |
|---|---|
| 실시간 게임(지연이 중요) | 파일 다운로드, 웹 API |
| 손실이 있는 무선·모바일 회선 | 안정적인 유선 |
| 일부 데이터를 비신뢰로 보낼 수 있음 | 전부 신뢰가 필요 |
| 대역폭보다 지연이 비쌈 | 대역폭이 비쌈 |

KCP는 **대역폭을 더 쓰고 지연을 얻는** 거래입니다(3장). 턴제 게임이나 채팅만 있다면
TCP나 WebSocket이 운영이 훨씬 쉽습니다.

### Q2. `conv` 가 무엇인가요?

**대화 번호**입니다. 24바이트 헤더의 첫 4바이트이며, 양 끝이 같아야 패킷을 받아들입니다(3장).

UDP는 연결이 없으므로 같은 포트로 아무 패킷이나 들어올 수 있습니다.
`conv` 가 "이 패킷이 우리 대화의 것인가"를 판단하는 첫 관문입니다.

이 라이브러리에서는 **서버가 할당**합니다(SYN_ACK에 실어 보냅니다).
`RawMode` 를 쓸 때만 직접 정합니다.

### Q3. 패킷이 안 옵니다. 무엇부터 봐야 하나요?

순서대로 의심하세요.

1. **`Update()` 를 부르고 있는가** — 가장 흔한 원인입니다(4장)
2. **방화벽** — UDP 인바운드가 막혀 있지 않은가
3. **포트 충돌** — 이미 그 포트를 쓰는 프로세스가 있는가
4. **`Send` 반환값** — `Backpressure` 로 버려지고 있지 않은가
5. **`conv` 불일치** — `Input` 이 -1을 돌려주고 있지 않은가

`session.Stats.SegmentsSent` 가 늘지 않으면 1번, 늘어도 상대가 못 받으면 2~3번입니다.

### Q4. "49일 문제"가 무엇인가요?

KCP의 시각은 `uint` 밀리초라 약 **49.7일**마다 0으로 돌아갑니다(랩어라운드).

```csharp
if (now >= next) { ... }         // ❌ 랩어라운드에서 영원히 거짓
if (Kcp.Itimediff(now, next) >= 0) { ... }   // ✅
```

이 라이브러리도 원래 이 버그가 있었습니다(진단 B-02).
`KcpClient`/`KcpServer` 를 쓰면 자동으로 처리되지만, 코어를 직접 쓴다면 반드시 `Itimediff` 를 쓰세요.

**49일 무중단 운영은 게임 서버에서 흔한 일**입니다.

### Q5. 여러 스레드에서 `Send` 해도 되나요?

**안 됩니다.** 인스턴스 1개는 소유 스레드 1개에서만 씁니다(5장).

```csharp
/// <b>스레딩 규약</b>: 인스턴스 1개는 소유 스레드 1개에서만 사용한다. 내부에 lock 이 없으므로
/// 여러 스레드에서 동시에 호출하면 상태가 깨진다.
```

락이 없는 것은 설계입니다 — 1만 세션에서 락 경합을 피하기 위해서입니다.
여러 스레드에서 보내야 한다면 **큐를 두고 소유 스레드가 꺼내 보내게** 하세요(6장).

## 플랫폼

### Q6. Unity에서도 쓸 수 있나요?

`netstandard2.1` 타깃이 있으므로 **원리적으로는 가능**합니다.

```bash
dotnet build -c Release src/KcpProject
# bin/Release/netstandard2.1/KcpProject.dll 을 Unity 의 Assets/Plugins 에 복사
```

다만 이 저장소는 **Unity를 공식 지원 대상으로 삼지 않습니다.**
게임 엔진 연동은 MonoGame으로 검증했습니다(부록 D).

Unity에서 쓸 때 주의할 점:

- Unity 2021.2+ 필요(netstandard2.1)
- IL2CPP에서 `Span`/`ArrayPool` 은 잘 동작하지만, 코드 스트리핑 설정을 확인하세요
- `AesGcm` 은 Unity의 Mono/IL2CPP 런타임에 없을 수 있습니다 → `IPacketCipher` 직접 구현

### Q7. Godot에서는요?

`netstandard2.1` 이라 Godot 4의 C# 프로젝트에서 참조할 수 있습니다.
`_Process` 안에서 `client.Update()` 를 부르면 MonoGame과 같은 방식입니다.

### Q8. 모바일에서 주의할 점은?

| 항목 | 권장 |
|---|---|
| MTU | **1200** (터널링 오버헤드) |
| `PingInterval` | 2초 (NAT 타임아웃이 15~30초로 짧음) |
| `interval` | 30ms 이하로 하되, 배터리를 고려 |
| IP 변경 | Wi-Fi ↔ LTE 전환 시 재접속 필요(17장) |

## 사용법

### Q9. 수신 콜백의 데이터를 나중에 쓰려면?

**복사해야 합니다.** 콜백이 끝나면 메모리가 무효입니다.

```csharp
server.ReliableReceived += (session, data) =>
{
    _queue.Enqueue(data.ToArray());   // ✅ 복사
    // _queue.Enqueue(data);          // ❌ 위험
};
```

### Q10. 큰 파일을 보내려면?

메시지 모드의 최대 크기는 `(RcvWnd − 1) × Mss` 입니다(기본 약 42KB).
그보다 크면 세 가지 방법이 있습니다.

1. **애플리케이션에서 쪼개기** — 가장 단순하고 권장됩니다
2. **윈도 키우기** — `WndSize(256, 256)` 이면 약 350KB
3. **스트림 모드** — 경계가 사라지므로 직접 프레이밍 필요

파일 전송이 주 용도라면 **TCP나 HTTP를 쓰는 편이 낫습니다.**

### Q11. `Backpressure` 가 나오면 어떻게 하나요?

**보내는 속도가 회선보다 빠릅니다.** 선택지는 세 가지입니다.

| 대응 | 언제 |
|---|---|
| 잠시 후 재시도 | 일시적 폭주(로딩 등) |
| 그냥 버림 | 비신뢰성 데이터(위치 스냅숏 등) |
| `MaxSendBacklog` 키움 | **권장하지 않음** — 지연만 늘어납니다 |

세 번째는 문제를 미루는 것일 뿐입니다. 큐에 쌓인 만큼이 전부 지연이 됩니다.

### Q12. 서버에서 특정 클라이언트를 끊으려면?

```csharp
session.Disconnect(reason: 42);   // FIN 송신 후 linger
```

`reason` 은 애플리케이션 정의 바이트입니다. 상대는 `CloseReason` 으로 받습니다.

### Q13. 접속자 수를 제한하려면?

```csharp
new KcpServerOptions { MaxSessions = 500 }
```

상한을 넘는 SYN은 **무응답으로 버립니다**(응답하면 증폭 공격에 이용될 수 있습니다).

IP당 세션 수 제한은 직접 구현해야 합니다 — `SessionConnected` 에서 세어 보고
초과하면 `Disconnect()` 하는 방식이 간단합니다.

## 문제 해결

### Q14. 로컬에서는 되는데 실제 서버에서 안 됩니다

| 증상 | 원인 |
|---|---|
| 연결 자체가 안 됨 | 방화벽(UDP), 보안 그룹, NAT |
| 연결은 되는데 큰 패킷만 안 감 | **MTU 블랙홀**(17장) → MTU 1200 |
| 가만히 있으면 끊김 | **NAT 타임아웃**(17장) → PingInterval 확인 |
| 인원이 몰리면 재전송 급증 | **수신 버퍼 오버플로**(17장) → 소켓 버퍼 확대 |

### Q15. 재전송률이 높습니다

먼저 **회선 문제인지 서버 문제인지** 가려야 합니다.

| 확인 | 회선 문제 | 서버 문제 |
|---|---|---|
| 일부 사용자만? | ✅ | ❌ |
| 전체 사용자? | ❌ | ✅ |
| 서버 CPU | 낮음 | **높음** |
| 인원과 상관관계 | 없음 | **있음** |

서버 문제라면 이벤트 핸들러에서 무거운 일을 하고 있지 않은지 보세요(6장 큐 패턴).

### Q16. "재전송은 0인데 데이터가 안 옵니다"

거의 항상 **`Send` 의 반환값을 무시한 경우**입니다.
백프레셔로 버려진 메시지는 애초에 보내지지 않았으므로 재전송할 것도 없습니다.

이 저장소의 부하 도구가 실제로 이 실수를 했습니다(17장).

### Q17. Gen2 GC가 자주 발생합니다

라이브러리의 정상 상태 송수신 경로는 **0 B/op** 입니다(14장, 벤치마크로 확인).
따라서 애플리케이션 쪽을 보세요.

흔한 범인:

- `data.ToArray()` (필요하지만 매 패킷이면 부담)
- `string` 연결·보간(로그!)
- LINQ(`.Where().Select().ToList()`)
- 람다 캡처

**로그가 가장 흔한 범인**입니다. 운영 환경에서는 디버그 로그를 끄세요.

## 상호운용

### Q18. kcp-go 서버에 붙을 수 있나요?

**코어는 바이트 호환**입니다. `RawMode` 를 켜면 됩니다.

```csharp
var options = new KcpSessionOptions
{
    RawMode = true,
    RawModeConv = 0x11223344,   // 서버와 약속한 값
};
```

다만 핸드셰이크·PING·FIN은 이 라이브러리 고유이므로 RawMode에서는 쓸 수 없습니다.
자세한 내용은 [부록 C](appendix-c-interop.md)를 보세요.

### Q19. 이 라이브러리끼리는 버전 호환이 되나요?

**코어 헤더(24바이트)는 영구 호환**입니다(불변 원칙).
전송 계층의 프레이밍은 `protocolVer` 바이트가 있어 버전을 협상할 여지를 남겼습니다.

현재 버전은 1이며, 다른 버전끼리는 핸드셰이크가 실패합니다.
