## 봐야 할 지표

이 라이브러리는 서버 상태를 주기적으로 알려 줍니다.

```csharp
// src/KcpCSharpR1.Transport/ServerMetrics.cs
public readonly struct KcpServerMetrics
{
    public uint TimestampMs { get; init; }
    public int SessionCount { get; init; }
    public ulong SegmentsSent { get; init; }
    public ulong RetransmitSegments { get; init; }
    public double RetransmitRatePercent => ...;
    public int RttP50 { get; init; }
    public int RttP95 { get; init; }
    public int RttP99 { get; init; }
    public ulong BytesSent { get; init; }
    public ulong BytesReceived { get; init; }
    public long FecRecoveredPackets { get; init; }
}
```

```csharp
server.MetricsSampled += metrics =>
    Console.WriteLine($"[{DateTime.Now:HH:mm:ss}] {metrics}");
```

```
[12:35:49] 세션 335, 재전송률 0.06%, RTT p50/p95/p99 = 4/7/8ms
```

포맷을 강요하지 않습니다. Prometheus든 CloudWatch든 자체 대시보드든 원하는 곳으로 보내세요.

### 경보 기준

| 지표 | 정상 | 주의 | 경보 |
|---|---|---|---|
| **재전송률** | < 1% | 1~5% | **> 5%** |
| **RTT p99** | 목표 지연의 2배 이내 | — | 목표의 3배 초과 |
| **세션 수** | 예상 범위 | 급증·급감 | 상한의 90% |
| **초당 바이트** | 예산 이내 | — | 회선 용량의 70% |

### p50이 아니라 p99를 보세요

평균과 중앙값은 **끊김을 숨깁니다.**

```
p50 30ms · p95 250ms · p99 517ms
```

이 회선의 "평균 경험"은 좋아 보이지만, **100번에 한 번은 0.5초 지연**입니다.
게임에서는 그 한 번이 죽음입니다.

실제로 위 수치는 1,000세션 부하 측정에서 나온 것입니다.
같은 서버가 300세션에서는 p99가 48.5ms였습니다 — **포화 지점을 넘으면 꼬리부터 무너집니다.**

### 재전송률로 진단하기

| 재전송률 | 해석 | 확인할 것 |
|---|---|---|
| 0% | 손실 없음 | 정상 |
| 1~3% | 무선/모바일의 정상 범위 | 정상 |
| **5%+** | 회선 문제 또는 **서버 과부하** | CPU, 틱 지연, 대역폭 |
| 20%+ | 사실상 못 쓰는 상태 | 회선 자체, FEC 검토(16장) |

**서버 과부하도 재전송률로 나타난다**는 점이 중요합니다.
서버가 밀려서 ACK를 제때 못 보내면 클라이언트가 재전송합니다.
회선은 멀쩡한데 재전송률이 오르면 CPU를 보세요.

## 용량 측정

### 부하 도구 사용법

```bash
# 받는 쪽
dotnet run -c Release --project samples/tools/LoadTest -- server

# 거는 쪽
dotnet run -c Release --project samples/tools/LoadTest -- \
  client --sessions 1000 --rate 20 --size 256 --duration 60 --csv result.csv
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--sessions` | 100 | 동시 세션 수 |
| `--rate` | 20 | 세션당 초당 메시지 수 |
| `--size` | 256 | 메시지 크기(바이트) |
| `--duration` | 60 | 측정 시간(초) |
| `--unreliable` | 꺼짐 | 비신뢰 채널 사용 |
| `--preset` | fast2 | `normal`/`fast`/`fast2`/`fast3` |
| `--csv` | 없음 | 결과를 CSV에 덧붙임 |
| `--sockbuf` | 65536 | 세션당 소켓 버퍼 |
| `--threads` | 자동 | 세션을 나눠 구동할 워커 스레드 수 |

### 리포트 읽기

```
┌───────────────── LoadTest 결과 ─────────────────
│ 설정      세션 1000, 20msg/s, 256B, 신뢰(KCP), 프리셋 fast2
│ 측정 시간 60.0초 (연결 성공 1000/1000, 끝까지 생존 1000)
├─────────────────────────────────────────────────
│ 메시지    보냄 970,627 / 에코 970,627 (16,175 msg/s)
│ 무결성    불일치 0건, 에코 손실 0.00%
│ 처리량    송신 40.34 Mbps / 수신 39.59 Mbps
│ 재전송    21,906 / 1,940,694 세그먼트 (1.13%)
│ RTT       p50 30ms  p95 250ms  p99 517ms  max 1770ms  (표본 970,627)
│ GC        Gen0 6 / Gen1 3 / Gen2 1
│ 메모리    관리 힙 219.6 MB, 작업 집합 386.3 MB
└─────────────────────────────────────────────────
```

**읽는 순서**가 있습니다.

1. **불일치** — 0이 아니면 다른 지표를 볼 필요도 없습니다. 심각한 버그입니다.
2. **끝까지 생존** — 연결 수보다 적으면 세션이 죽었다는 뜻입니다.
3. **에코 손실** — 신뢰 채널이면 0%여야 합니다.
4. **재전송률 / RTT p99** — 여유가 있는지.
5. **Gen2** — 0이어야 합니다.

### 어디까지가 우리 용량인가

같은 PC에서 클라·서버를 함께 돌린 실측:

| 세션 | 재전송률 | RTT p99 | Gen2 | 판정 |
|---:|---:|---:|---:|---|
| 300 | 0.00% | 48.5ms | 0회 | **여유** |
| 1,000 | 1.13% | 517ms | 1회 | 포화 |

"1,000세션이 된다"와 "1,000세션이 쾌적하다"는 다릅니다.
**목표 RTT p99를 정하고, 그것을 지키는 최대 세션 수**가 진짜 용량입니다.

> 이 측정은 클라이언트와 서버가 **같은 PC**에 있습니다. 서버 단독 용량이 아닙니다.
> 실제 용량을 재려면 부하 생성기를 다른 장비에 두어야 합니다.

## 측정기를 먼저 의심하라

이 저장소에서 1,000세션 측정을 하면서 **세 번 연속으로 도구 쪽 버그**를 만났습니다.
전부 "라이브러리가 이상하다"고 오해하기 딱 좋은 증상이었습니다.

### ① "1,000개 연결했는데 서버에는 325개뿐"

**증상**: 클라이언트는 1000/1000 연결 성공이라는데 서버 로그의 세션 수는 325에서 멈춤.

**원인**: 세션을 순차로 여는 데 십수 초가 걸리는데, 그동안 **먼저 연결된 세션들을
`Update()` 하지 않았습니다.** keepalive를 못 보내니 서버가 10초 타임아웃으로 끊었습니다.

**교훈**: 접속 단계에서도 이미 연결된 세션은 계속 돌려야 합니다.

```csharp
// samples/tools/LoadTest/Program.cs
// ★ 이미 연결된 세션들도 계속 돌려 줘야 한다.
// 세션을 순차로 여는 동안(1,000개면 십수 초) 앞서 연결된 세션이 keepalive 를 못 보내면
// 서버가 SessionTimeout(기본 10초)으로 끊어 버린다.
if ((i + 1) % 16 == 0)
{
    foreach (var existing in sessions) existing.Client.Update();
}
```

### ② "재전송은 0인데 데이터가 안 온다"

**증상**: 재전송률 0.00%인데 에코가 40% 부족.

**원인**: 서버가 `session.Send()` 의 반환값을 무시했습니다.
백로그가 상한을 넘으면 라이브러리는 `Backpressure` 를 돌려주고 **메시지를 받지 않습니다.**
그것을 무시하니 "보냈다고 생각했지만 실제로는 버려진" 메시지가 쌓였습니다.

**교훈**: `Send` 의 반환값을 반드시 확인하세요. 지금은 버린 개수를 셉니다.

```csharp
// samples/tools/LoadTest/Program.cs
server.ReliableReceived += (session, data) =>
{
    if (session.Send(data.Span) == KcpSendResult.Ok) Interlocked.Increment(ref echoed);
    else Interlocked.Increment(ref dropped);
};
```

### ③ 측정기가 GC를 유발했다

**증상**: Gen2 수집이 1회 발생. "라이브러리가 할당을 하나?"

**원인**: RTT 표본 96만 개를 `List<double>` 에 쌓았습니다. **측정 도구 자신이** 만든 GC였습니다.

**교훈**: 1ms 폭 고정 히스토그램(세션당 8KB)으로 바꿔 실행 중 추가 할당을 없앴습니다.

```csharp
// samples/tools/LoadTest/LatencyHistogram.cs
/// <para>
/// 표본을 리스트에 그대로 쌓으면 측정 자체가 GC 를 유발한다. 실제로 1,000세션·60초 실행에서
/// RTT 표본이 96만 개까지 늘어 <b>측정 도구 때문에</b> Gen2 수집이 일어났다.
/// (측정 대상이 아니라 측정기가 만든 노이즈다.)
/// </para>
```

**세 번 모두 라이브러리가 아니라 측정 코드의 결함**이었습니다.
부하 측정에서 이상한 숫자가 나오면 **측정기부터 의심하세요.**

## 흔한 장애 사례집

### ① MTU 블랙홀

**증상**: 연결은 되는데 게임을 시작하면 멈춘다. 로비는 되는데 인게임이 안 된다.

**원인**: 경로 어딘가의 MTU가 우리 설정보다 작습니다. 큰 패킷만 조용히 사라집니다.
작은 패킷(핸드셰이크, PING)은 잘 가므로 **연결은 성공합니다.**

**진단**: 세션은 살아 있는데(PING/PONG 정상) 큰 메시지만 재전송이 반복됩니다.
재전송률이 특정 사용자에게서만 100%에 가깝습니다.

**대응**: MTU를 1200으로 내립니다. 모바일 사용자가 많으면 처음부터 1200을 쓰세요.

```csharp
new KcpSessionOptions { Mtu = 1200 }
```

### ② NAT 타임아웃

**증상**: 가만히 있으면(로딩 화면, 인벤토리 정리) 끊긴다. 조작 중에는 멀쩡하다.

**원인**: 공유기나 이동통신망이 UDP 매핑을 지웠습니다. 서버가 보낸 패킷이 도달하지 못합니다.

**진단**: 클라이언트 → 서버는 가는데(서버가 받음) 서버 → 클라이언트가 안 옵니다.
"유휴 시간이 길었던" 사용자에게만 발생합니다.

**대응**: `PingInterval` 을 NAT 타임아웃보다 짧게. 기본 2초는 안전하지만,
배터리 때문에 늘렸다면 **15초를 넘기지 마세요.**

| 환경 | 흔한 UDP 매핑 유지 시간 |
|---|---|
| 가정용 공유기 | 30초 ~ 5분 |
| 모바일(LTE/5G) | 30초 안팎, 짧으면 15초 |

### ③ 모바일 IP 변경

**증상**: 지하철에서 나오거나 Wi-Fi ↔ LTE 전환 시 끊긴다.

**원인**: 클라이언트의 IP·포트가 바뀌었습니다. 서버의 세션 테이블은 주소를 키로 쓰므로
**다른 사람으로 보입니다.**

**대응**: 세션 마이그레이션이 필요합니다. **암호화가 켜져 있을 때만 안전하게 할 수 있습니다** —
인증된 패킷이 새 주소에서 오면 테이블 키를 갱신하는 방식입니다.
암호화 없이 하면 **주소만 위조해 남의 세션을 가로챌 수 있습니다.**

> 이 라이브러리는 아직 세션 마이그레이션을 제공하지 않습니다.
> 지금은 재접속(11장의 토큰 방식)으로 대응하세요.

### ④ 수신 버퍼 오버플로

**증상**: 평소엔 멀쩡한데 인원이 몰리는 순간(레이드 보스, 공성전) 재전송률이 급등한다.

**원인**: 커널 수신 버퍼가 가득 차 패킷이 **조용히 버려졌습니다.**
애플리케이션에는 아무 오류도 나지 않습니다.

**진단**: 리눅스라면

```bash
netstat -su | grep -i "receive buffer errors"
```

**대응**: 소켓 버퍼를 키웁니다. 이 라이브러리는 기본 1MB입니다.

```csharp
new KcpServerOptions
{
    SocketReceiveBufferSize = 4 << 20,   // 4MB
    SocketSendBufferSize = 4 << 20,
}
```

OS 상한도 함께 올려야 합니다.

```bash
sudo sysctl -w net.core.rmem_max=8388608
sudo sysctl -w net.core.wmem_max=8388608
```

> 근본 대책은 **수신 루프가 밀리지 않게** 하는 것입니다. 이벤트 핸들러에서 무거운 일을 하고 있지 않은지
> 확인하세요(6장의 큐 패턴).

## Windows 특유의 함정

```csharp
// src/KcpCSharpR1.Transport/UdpSocketTransport.cs
// Windows: ICMP Port Unreachable 로 인한 수신 예외를 막는다.
if (RuntimeInformation.IsOSPlatform(OSPlatform.Windows))
{
    try
    {
        socket.IOControl(SIO_UDP_CONNRESET, new byte[] { 0 }, null);
    }
    catch (SocketException) { }
}
```

Windows에서는 상대가 사라져 ICMP Port Unreachable이 오면 **다음 수신 호출이 예외를 던집니다.**
UDP인데 말입니다. 이 설정을 안 하면 클라이언트 하나가 죽을 때마다 서버 수신 루프가 터집니다.

라이브러리가 알아서 처리하지만, 직접 소켓을 다룬다면 반드시 기억하세요.

## 배포 체크리스트

- [ ] 소켓 버퍼를 서버 규모에 맞게 설정했는가(기본 1MB, OS 상한도 함께)
- [ ] 포트가 방화벽에서 열려 있는가(UDP!)
- [ ] `MaxSessions` 가 서버 용량에 맞는가
- [ ] `PingInterval` 이 NAT 타임아웃보다 짧은가
- [ ] MTU를 대상 사용자에 맞게 정했는가(모바일 1200)
- [ ] 서버 틱 예산 안에서 도는가(부하 도구로 확인)
- [ ] 지표를 어디로 보낼지 정했는가
- [ ] 재전송률·RTT p99 경보를 걸어 두었는가
- [ ] 로그에 개인정보·키가 찍히지 않는가

## 요약

- **p99를 보세요.** 평균은 끊김을 숨깁니다.
- 재전송률 5% 초과는 회선 문제일 수도, **서버 과부하**일 수도 있습니다.
- "1,000세션이 된다"와 "쾌적하다"는 다릅니다. **목표 p99를 지키는 최대치**가 용량입니다.
- 부하 측정에서 이상한 숫자가 나오면 **측정기부터 의심하세요**(세 번 다 그랬습니다).
- 장애 4종: **MTU 블랙홀 / NAT 타임아웃 / IP 변경 / 수신 버퍼 오버플로**.
