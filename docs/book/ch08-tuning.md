# 8장. 파라미터 튜닝

> **학습 목표**
> 1. `NoDelay` 네 인자의 정확한 의미를 알고 프리셋을 고를 수 있습니다.
> 2. 대역폭·RTT로부터 윈도 크기를 계산할 수 있습니다.
> 3. MTU를 왜 1400 또는 1200으로 잡는지 설명하고, 부하 도구로 직접 비교 측정할 수 있습니다.

## `NoDelay(nodelay, interval, resend, nc)`

```csharp
// src/KcpProject/Kcp.cs
/// <param name="nodelay_">0: 비활성(기본), 1: 활성.</param>
/// <param name="interval_">내부 갱신 간격(ms). 기본 100.</param>
/// <param name="resend_">0: 빠른 재전송 끔(기본), n: 중복 ACK n회에 재전송.</param>
/// <param name="nc_">0: 혼잡 제어 사용(기본), 1: 사용 안 함.</param>
public int NoDelay(int nodelay_, int interval_, int resend_, int nc_)
```

### ① nodelay — RTO 증가 방식

RTO(재전송 대기 시간)가 만료되면 다시 보내고, RTO를 늘립니다. 얼마나 늘리느냐가 다릅니다.

```csharp
// src/KcpProject/Kcp.cs
else if (_itimediff(current, segment.resendts) >= 0) // RTO 만료
{
    needsend = true;
    if (nodelay == 0)
        segment.rto += rx_rto;          // 2배 (TCP 방식)
    else
        segment.rto += rx_rto / 2;      // 1.5배 (더 공격적)
    ...
}
```

또 최소 RTO도 달라집니다.

| nodelay | 최소 RTO | 백오프 |
|---|---|---|
| 0 | 100ms | 2배씩 |
| 1 | **30ms** | 1.5배씩 |

`nodelay=1` 은 **손실을 더 빨리 포기하고 다시 보냅니다.** 지연은 줄지만
회선이 이미 막혀 있을 때는 불난 집에 부채질이 될 수 있습니다.

### ② interval — 내부 갱신 주기

`Update()` 가 실제로 일을 하는 최소 간격입니다.
10ms로 잡으면 최대 10ms 안에 ACK와 재전송이 나갑니다.

| interval | 지연 | CPU / ACK 트래픽 / 배터리 |
|---|---|---|
| 10ms | 가장 낮음 | 가장 높음 |
| 20ms | 낮음 | 보통 |
| 40ms | 보통 | 낮음 |
| 100ms(기본) | 높음 | 가장 낮음 |

**모바일에서는 30ms 이하를 권합니다.** 그보다 짧으면 배터리 소모가 눈에 띕니다.

### ③ resend — 빠른 재전송 임계값

같은 세그먼트에 대한 중복 ACK를 n번 받으면 RTO를 기다리지 않고 재전송합니다.
보통 2를 씁니다. 0이면 끕니다.

### ④ nc — 혼잡 제어 끄기

`nc=1` 이면 혼잡 윈도(cwnd)를 무시하고 송신 윈도만큼 밀어 넣습니다.

> **주의**: 이것은 "내 트래픽이 남에게 폐를 끼쳐도 상관없다"는 선언입니다.
> 사설망이나 소규모라면 괜찮지만, **공용 인터넷에서 대규모로 쓰면 손실이 자기 증폭**합니다
> (손실 → 재전송 → 더 혼잡 → 더 손실). 게임 트래픽이 작아서 관행적으로 쓰지만,
> 규모가 커지면 반드시 다시 검토하세요.

## 프리셋 4종

| 프리셋 | 호출 | 용도 |
|---|---|---|
| `normal` | `NoDelay(0, 40, 2, 1)` | 일반 |
| `fast` | `NoDelay(0, 30, 2, 1)` | 절충 |
| `fast2` | `NoDelay(1, 20, 2, 1)` | 실시간성 우선 |
| `fast3` | `NoDelay(1, 10, 2, 1)` | 최저 지연(CPU·대역폭 비용 증가) |

부하 도구에도 그대로 들어 있습니다.

```csharp
// samples/tools/LoadTest/Options.cs
(int nodelay, int interval, int resend, int nc) preset = Preset switch
{
    "normal" => (0, 40, 2, 1),
    "fast" => (0, 30, 2, 1),
    "fast2" => (1, 20, 2, 1),
    "fast3" => (1, 10, 2, 1),
    _ => throw new ArgumentException($"알 수 없는 프리셋: {Preset}"),
};
```

## 윈도 크기 산정

**대역폭-지연 곱(BDP)** 을 MTU로 나누면 필요한 윈도가 나옵니다.

```
필요 윈도(패킷) = 대역폭(bps) × RTT(초) ÷ 8 ÷ MTU(바이트)
```

예: 10Mbps, RTT 100ms, MTU 1400

```
10,000,000 × 0.1 ÷ 8 ÷ 1400 ≈ 89 패킷 → 128 로 올림
```

윈도가 이보다 작으면 **회선을 다 못 씁니다**(보내고 ACK를 기다리느라 놀게 됩니다).
크면 메모리를 더 쓰고, 혼잡 시 더 많이 밀립니다.

```csharp
session.Kcp?.WndSize(128, 128);
// 또는 옵션으로
new KcpSessionOptions { SendWindow = 128, ReceiveWindow = 128 }
```

> **게임 트래픽은 대개 작습니다.** 초당 20패킷 × 200바이트면 32kbps라 기본 윈도로 충분합니다.
> 윈도를 키워야 하는 것은 **큰 파일이나 맵 데이터를 전송할 때**입니다.

## MTU — 왜 1400인가

이더넷 MTU는 1500바이트입니다. 여기서 빼야 할 것들이 있습니다.

| 항목 | 크기 |
|---|---|
| IPv4 헤더 | 20 B |
| UDP 헤더 | 8 B |
| **남는 것** | **1472 B** |

그런데 왜 1400일까요? 중간 경로에 **터널링**이 있을 수 있기 때문입니다.

| 터널 | 추가 오버헤드 |
|---|---|
| PPPoE(가정용 인터넷) | 8 B |
| IPv6 헤더(IPv4 대신) | +20 B |
| VPN(IPSec 등) | 20~80 B |
| 모바일망 캡슐화(GTP) | 수십 B |

1400은 이 대부분을 흡수하는 안전한 값입니다. **모바일은 1200을 권합니다.**

### MTU 블랙홀

MTU를 넘는 패킷은 어떻게 될까요? IPv4에서는 라우터가 조각화하거나
"Fragmentation Needed" ICMP를 돌려줍니다. 그런데 **많은 방화벽이 그 ICMP를 막습니다.**

결과는 최악입니다.

- 작은 패킷은 잘 갑니다(핸드셰이크 성공)
- 큰 패킷만 조용히 사라집니다
- **"연결은 되는데 게임을 시작하면 멈춘다"**

그래서 보수적으로 잡습니다. 1400에서 문제가 있으면 1200으로 내려 보세요.

```csharp
new KcpSessionOptions { Mtu = 1200 }
```

## 장르별 권장 설정

| 장르 | 프리셋 | WndSize(snd,rcv) | MTU | 채널 전략 |
|---|---|---|---|---|
| 턴제·카드·퍼즐 | `normal` | 32, 32 | 1400 | 전부 신뢰 채널 |
| MMORPG 필드 | `fast` | 128, 128 | 1400(모바일 1200) | 전투 판정=신뢰, 주변 이동=비신뢰 |
| 실시간 액션·대전 | `fast2` | 256, 256 | 1200 | 입력/판정=신뢰, 스냅숏=비신뢰 |
| FPS·레이싱 | `fast3` | 256, 256 | 1200 | 스냅숏=비신뢰(+FEC 검토), 이벤트=신뢰 |
| 모바일 공통 | `interval ≤ 30` | — | 1200 | PingInterval 2s, SessionTimeout 10s |

이 표는 **출발점**입니다. 반드시 자기 게임에서 재 보세요.

## 직접 재 보기

부하 도구가 프리셋 비교 실습을 지원합니다.

```bash
# 서버
dotnet run -c Release --project samples/tools/LoadTest -- server

# 프리셋별로 30초씩
for p in normal fast fast2 fast3; do
  dotnet run -c Release --project samples/tools/LoadTest -- \
    client --sessions 200 --duration 30 --preset $p --csv preset.csv
done
```

CSV에 한 줄씩 쌓이므로 스프레드시트로 비교하기 좋습니다.

```
timestamp,sessions,rate,size,channel,preset,seconds,msg_sent,msg_echoed,...,rtt_p50,rtt_p95,rtt_p99,...
2026-08-25T12:55:47,1000,20,256,reliable,fast2,60.01,970627,970627,...,30,250,517,...
```

**손실을 걸고 재야 의미가 있습니다.** 무손실 회선에서는 프리셋 차이가 거의 나지 않습니다.

```bash
sudo tc qdisc add dev lo root netem loss 5% delay 50ms   # Linux
```

Windows에서는 [clumsy](https://jagt.github.io/clumsy/)를 씁니다.

### 무엇을 볼 것인가

| 지표 | 의미 |
|---|---|
| **RTT p95 / p99** | 평균이 아니라 **꼬리**를 봅니다. 게임 체감은 최악의 순간이 좌우합니다 |
| 재전송률 | 프리셋이 공격적일수록 늘어납니다. 지연과의 맞바꿈 |
| 처리량(Mbps) | 대역폭 예산 안에 있는지 |
| CPU | `interval` 을 줄이면 서버 CPU가 늘어납니다 |

**p50이 좋아졌는데 p99가 나빠졌다면 대개 손해입니다.**

## 흔한 튜닝 실수

### ① 무손실 환경에서 튜닝하기

로컬(RTT 1ms, 손실 0%)에서는 어떤 설정이든 잘 돕니다.
**실제 사용자의 회선을 흉내 내고** 재세요.

### ② interval 을 무작정 줄이기

10ms로 줄이면 지연은 좋아지지만 세션 1만 개에서 CPU가 4배가 됩니다.
`Check()` 기반 스케줄러가 있으니 실제로는 그렇게까지 늘지 않지만, 재 보고 판단하세요.

### ③ 윈도를 무작정 키우기

윈도가 크면 **밀렸을 때 더 많이 밀립니다.** 큐에 쌓인 만큼이 전부 지연이 됩니다.
게임에서는 오히려 **작은 윈도 + 백프레셔**가 나은 경우가 많습니다.

### ④ 한 번에 여러 개 바꾸기

프리셋·윈도·MTU를 동시에 바꾸면 무엇이 효과였는지 모릅니다.
**하나씩 바꾸고 매번 재세요.** 이 저장소의 성능 작업도 그렇게 했습니다(14장).

## 요약

- `nodelay=1` 은 RTO 백오프를 1.5배로, 최소 RTO를 30ms로 낮춥니다 — 공격적이지만 빠릅니다.
- `interval` 은 지연과 CPU·배터리의 맞바꿈입니다. 모바일은 30ms 이하.
- **`nc=1`(혼잡 제어 끄기)은 규모가 커지면 재검토**해야 합니다.
- 윈도 = 대역폭 × RTT ÷ MTU. 게임 트래픽은 대개 기본값으로 충분합니다.
- MTU는 1400(모바일 1200). **MTU 블랙홀은 "연결은 되는데 멈추는" 증상**으로 나타납니다.
- 튜닝은 **손실을 걸고, 하나씩 바꾸고, p99를 보며** 합니다.
