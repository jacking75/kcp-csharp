# 샘플 ④ MoveSync `★4 중상급`

20Hz 틱 서버와 스냅숏 보간. **실시간 동기화의 표준형**이자, 이 라이브러리에서
**신뢰 채널과 비신뢰 채널을 나눠 쓰는 법**을 배우는 샘플이다.

## 실행

```bash
dotnet run --project samples/04-MoveSync/Server
dotnet run --project samples/04-MoveSync/Client -- 127.0.0.1 alice
dotnet run --project samples/04-MoveSync/Client -- 127.0.0.1 bob
```

UDP **27004** 포트. 최대 16명.

| 조작 | 동작 |
|---|---|
| `WASD` / 방향키 | 이동 |
| `F1` | **보간 on/off 토글** — 이 샘플의 핵심 실습 |
| `ESC` | 종료 |

## 배우는 것

- **고정 틱 루프**(20Hz)와 가변 프레임 클라이언트(60Hz)의 관계
- **채널 분리** — 무엇을 신뢰로, 무엇을 비신뢰로 보낼지 판단하는 기준
- 스냅숏 설계와 **대역폭 계산**
- **클라이언트 보간** — 100ms 늦게 재생해 부드러움을 사는 거래
- 늦게 온 스냅숏 버리기(틱 번호 비교)

## 채널을 나누는 기준

| 데이터 | 채널 | 왜 |
|---|---|---|
| 입장/퇴장, 내 ID 배정, 채팅 | **신뢰(KCP)** | 놓치면 게임이 망가진다. 한 번만 도착하면 되고 순서가 중요하다 |
| 입력(10Hz), 스냅숏(20Hz) | **비신뢰(RAW)** | 50~100ms 뒤면 새 것이 온다. 낡은 것을 재전송받아 기다릴 이유가 없다 |

스냅숏을 신뢰 채널로 보내면 어떻게 되는지는 책 7장에서 실험한다. 요약하면
**패킷 하나가 유실됐을 때 그 뒤의 모든 스냅숏이 도착해 있어도 순서 때문에 막힌다**(head-of-line 블로킹).
"최신 위치만 알면 되는" 데이터에는 최악의 성질이다.

## 보간을 직접 껐다 켜 보기

`F1` 을 누르면 HUD의 `INTERP` 가 `OFF` 로 바뀐다.

- **OFF** — 받은 최신 스냅숏을 그대로 그린다. 초당 20번만 위치가 바뀌어 **뚝뚝 끊긴다**.
- **ON** — 일부러 100ms 과거를 재생하며 두 스냅숏 사이를 선형 보간한다. 60Hz로 **부드럽다**.

100ms의 지연을 내주고 부드러움을 산 것이다. 이 거래가 실시간 게임 동기화의 출발점이다.

## 스냅숏 패킷과 대역폭

```
[u16 len][u8 0x84][u32 tick][u8 count]{ [u32 id][f32 x][f32 y][u8 dir] } × count
```

| 항목 | 크기 |
|---|---|
| 엔티티 1개 | id 4 + x 4 + y 4 + dir 1 = **13 B** |
| 헤더 | tick 4 + count 1 = 5 B |
| 16인 페이로드 | 5 + 13 × 16 = **213 B** |

20Hz 로 보내므로 **클라이언트 1명이 받는 양**은

```
213 B × 20회/초 = 4,260 B/s ≈ 34 kbps   (페이로드 기준)
```

여기에 RAW 프레임 헤더 5B + UDP/IP 28B 가 패킷마다 붙으므로 실제 회선 사용량은

```
(213 + 5 + 28) B × 20 = 4,920 B/s ≈ 39 kbps
```

**서버의 업로드**는 이것의 16배(모든 클라이언트에게 보내므로) ≈ **630 kbps**.
인원이 늘면 <b>N²</b> 로 증가한다는 점이 중요하다 — 100명이면 24 Mbps다.
그래서 실제 게임은 관심 영역(AOI)으로 보낼 대상을 잘라 낸다.

## 코드 지도

| 파일 | 역할 |
|---|---|
| `Shared/Protocol.cs` | 메시지 정의 + 채널 선택 근거 주석 |
| `Server/WorldServer.cs` | 입력 적용 → 월드 진행 → 스냅숏 브로드캐스트 |
| `Server/Program.cs` | 드리프트 없는 고정 틱 루프 |
| `Client/SnapshotBuffer.cs` | 보간 버퍼(늦은 스냅숏 폐기 포함) |
| `Client/MoveSyncGame.cs` | 입력 송신·렌더링·HUD |

## 직접 확인해 볼 것

1. **틱 처리 시간** — 서버가 5초마다 `틱 처리 최대 N ms` 를 찍는다. 4인 기준 1ms 안쪽이다.
   (완료 조건: 16인에서 5ms 미만)
2. **손실을 걸어 본다** — clumsy나 `tc netem` 으로 손실 10%를 걸어도 위치 동기화가 유지된다.
   비신뢰 채널이라 유실된 스냅숏을 기다리지 않고 다음 것으로 넘어가기 때문이다.
   HUD의 `DROPPED` 는 **순서가 뒤바뀌어 버린** 스냅숏 수다.
3. **입력 주기를 바꿔 본다** — `ProtocolLimits.InputRate` 를 5Hz로 낮추면 조작이 둔해진다.
   30Hz로 올리면 부드러워지지만 상행 대역폭이 3배가 된다.

## 이 샘플이 아직 하지 않는 것

내 캐릭터도 **서버 스냅숏을 기다렸다가** 움직인다. 즉 내 입력이 RTT만큼 늦게 반영된다.
로컬에서는 티가 안 나지만 RTT 100ms 환경에서는 확실히 둔하다.
이것을 없애는 **클라이언트 예측**은 샘플 ⑤에서 다룬다.
